# 문제 의도 분류 (Intent Classify)

막연한 업무 요청을 구조화된 문제 정의로 전환하는 JOYLAB 문제해결 프레임워크의 첫 단계. "무엇을 원하는가"를 먼저 명확히 하지 않으면 좋은 실행 결과도 무의미하다.

## 분해 구조

각 요청을 아래 6개 축으로 분해한다.

```
Job        요청자가 실제로 해결하려는 과업은 무엇인가
Outcome    무엇이 나오면 "해결됐다"고 느끼는가
Why Now    왜 지금 이 요청을 하는가 (트리거 이벤트)
Limits     시간/인력/데이터/권한 상 제약은 무엇인가
Audience   결과물을 누가 보고, 누구에게 보고하는가
Baseline   현재 상태는 어떤가 (수치/정성 모두)
```

## 업무 유형 분류

요청을 아래 8개 CS Ops 도메인 중 하나 이상으로 매핑한다. 라우팅 결과는 project-spec 단계에서 실행 스킬/커맨드 선택에 사용된다.

| 업무 유형 | 트리거 키워드 예시 | 라우팅 대상 플러그인 |
|-----------|---------------------|----------------------|
| 품질분석 | 품질, 평가, AutoQA, 컴플라이언스 | cs-quality-analysis |
| 코칭 | 코칭, 피드백, 개선계획 | cs-coaching |
| 성과관리 | KPI, T-NPS, 벤치마킹, 목표 | cs-performance |
| VOC | 불만, 컴플레인, 감성, 넛지 | cs-voc |
| STT분석 | 녹취, STT, 대화분석, 개인정보 | cs-stt |
| 운영기획 | 인력배치, 프로세스, 회의록, OKR | cs-operations |
| 리포팅 | 보고서, 주간, 월간, 경영진 보고 | cs-reporting |
| 범용/도구 | 도구, 명세서, 목데이터, 교정 | cs-toolkit |

하나의 요청이 여러 도메인에 걸치는 경우(예: "품질 낮은 상담사 찾아서 코칭 계획까지") 우선순위 순서로 나열한다.

## 출력 형식

ALWAYS use this exact template:

```
## Intent 분석

**원 요청:** [사용자 입력 그대로 인용]

| 축 | 내용 |
|----|------|
| Job | [실제 해결 과업] |
| Outcome | [완료 판단 기준] |
| Why Now | [트리거 이벤트 / 불명확 시 "미확인 — Interview 단계에서 확인 필요"] |
| Limits | [제약 / 불명확 시 동일 표기] |
| Audience | [결과 소비자] |
| Baseline | [현재 상태 / 불명확 시 동일 표기] |

**업무 유형:** [1순위 도메인] (+ [2순위 도메인, 있는 경우])
**추천 라우팅:** [플러그인명] → [관련 스킬/커맨드]
**정보 충분도:** [충분 — Interview 생략 가능 / 부족 — Interview 필요]
```

## 판단 지침

"불명확"을 추측으로 채우지 않는다 — 반드시 "미확인"으로 표기하고 다음 단계(joylab-interview)로 넘긴다.
Job과 Outcome이 이미 요청 안에 명시돼 있으면 재확인 질문을 만들지 않는다.
Baseline이 숫자로 주어지지 않았다고 Interview 필수 사유로 자동 처리하지 않는다 — 그 프로젝트 유형에서 실제로 결과 품질을 바꾸는 정보인지 먼저 판단한다.

## 사용 예시

- `상담 품질이 요즘 안 좋아진 것 같은데 뭐부터 봐야 할지 모르겠어요`
- `이번 달 VOC가 늘었는데 원인을 모르겠습니다. 프로젝트로 정리해줘`
- `신입 상담사 3명 코칭 계획을 세워야 하는데 어디서부터 시작할지 감이 안 옵니다`
